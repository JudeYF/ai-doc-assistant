# 治安管理处罚法问答评测集

这是 `ai-doc-assistant` 的离线评测集和跑分脚本。题目全部依据当前索引里的那一份 PDF——`data/中华人民共和国治安管理处罚法.pdf`（2005 年通过、2012 年修正，共 119 条）——编写，证据是从索引文本里原样截取的，没有另外编造法条。

本目录只新增评测文件，不改项目代码，也不会在评测时重建 `data/chroma_db`。

## 语料和切分现状（编写时核对过）

- 仓库里目前只有这一份法律 PDF，Chroma collection 名是 `china_public_security_law`，共 **30** 个片段。
- 切分按章 / 节 / 条的正则分隔，`chunk_size=800`、`chunk_overlap=50`。短条文经常被合并进同一个片段，所以一个 chunk 里可能有多条。
- **片段的 metadata 只有 `source`（PDF 的绝对路径），没有条号、没有 chunk id。** 因此命中不能按 metadata 对条，脚本改为从片段正文里识别作为标题出现的「第X条」。
- 正文里的交叉引用（例如「依照本法第四十三条第一款」）不会被当成该条已被检索到。
- 个别片段几乎只有章节标题（例如「第三章 违反治安管理的行为和处罚」「第四章 处罚程序」），检索价值很低。
- PDF 抽取后仍残留少量页码痕迹（如 `—10`），清洗函数没有去干净。证据截取时避开了这些杂质，但索引原文里还在。

## 评测集

文件：`eval/eval_set.jsonl`，每行一条 JSON，共 **40** 题。

| 题型 | 字段 `type` | 题数 | 说明 |
| --- | --- | --- | --- |
| 单条事实题 | `single_article` | 20 | 答案在一条里 |
| 多条 / 多跳 | `multi_article` | 8 | 需要两条或以上，或一条指向另一条 |
| 口语转述 | `paraphrase` | 6 | 问法更像用户口述，金标仍是具体条文 |
| 不可回答 | `unanswerable` | 6 | 材料里没有答案，期望明确说明未找到、不要编造 |

字段含义：

- `id`：`e01`–`e40`
- `question`：中文问题
- `reference_answer`：参考答案（只根据本法条文）
- `source.doc`：文件名 `中华人民共和国治安管理处罚法.pdf`
- `source.articles`：金标条号，中文数字，如 `["第五十条"]`。不可回答题为空列表
- `gold_evidence`：从该条原文截取的连续片段，保留 PDF 里的换行，便于核验。匹配时会去掉空白再比较
- `type` / `answerable`

不可回答题里有两道「看起来相关、但本法其实没给出答案」的题：申请行政复议的具体期限（第一百零二条只说可以申请，没写几天），以及危险驾驶罪的定罪量刑（第十五条只规定醉酒的人违反治安管理应当处罚）。这两道用来看模型会不会用其他法律知识补数字。

## 怎么跑

在仓库根目录、已激活项目虚拟环境的前提下执行。

先确认：

1. `data/chroma_db` 已经存在（没有的话先跑一次 `python scripts/init_db.py`，这不是本脚本做的）。
2. 本机 Ollama 已启动，并且已加载 `.env` 里的嵌入模型（默认 `bge-m3:latest`）。检索时要对查询向量化，Ollama 没开会失败。
3. **不必**启动 FastAPI 或 Streamlit。`/chat` 接口只返回回答、不返回检索片段，没法算 Hit@k，所以脚本直接调用 `app.rag.retriever.get_retrieval_result`。

只评检索（默认，不消耗对话模型额度）：

```bash
source .venv/bin/activate
python eval/run_eval.py
```

同时生成回答，并统计引用对不对、不可回答题会不会拒答：

```bash
python eval/run_eval.py --with-answers
```

再加上用同一套 LLM 配置做正确性打分（0 / 0.5 / 1）：

```bash
python eval/run_eval.py --with-answers --with-llm-judge
```

对话模型读的是项目 `.env` 里的 `LLM_API_KEY`、`LLM_MODEL`、`LLM_BASE_URL`（示例配置是智谱 GLM，以你本机 `.env` 为准）。生成回答时 history 为空，也 **不会** 写入 `data/chat_history.db`。

常用参数：

- `--limit 5` 先跑前 5 条，检查环境
- `--ids e01,e21,e35` 只跑指定题
- `--k 6` Hit@k 的最大 k，默认 6
- `--eval-set` / `--out-dir` 自定义路径

结果写到 `eval/results/`：

- `summary.md`、`summary.json`：汇总表
- `per_item.jsonl`：每题的检索片段、命中名次、（如有）模型回答和引用

## 指标含义

检索指标只在 **可回答题** 上计算（`single_article`、`multi_article`、`paraphrase`）。

- **Hit@k**：前 k 个片段里，是否至少出现一条金标条文标题。
- **Article-Recall@k**：金标条文中，有多少比例出现在前 k 个片段里，再对题目取平均。多跳题用这条看是不是只找回了一部分。
- **MRR**：第一条命中金标条文的片段名次的倒数，再平均。第 1 名命中为 1，第 2 名为 0.5，未命中为 0。

注意：项目里的 `get_retrieval_result(query, k=6)` **并没有使用** `k` 参数，向量检索和 BM25 都在初始化时写死 `k=6`。脚本按返回列表的现有排序计算 Hit@1 / Hit@3 / Hit@5 / Hit@6。

回答指标（需 `--with-answers`）：

- **引用命中**：可回答题的回答文本里，是否至少写到了一条金标「第X条」（阿拉伯数字也会规范化成中文条号再比）。
- **引用精确率 / 召回率**：回答里引用的条文与金标条文的交集比例。
- **拒答准确率**：不可回答题中，回答被启发式规则判定为「材料中没有 / 未规定 / 不能编造」等的比例。这是规则匹配，不是法律审校，漏判或误判都可能发生。
- **LLM judge 均分**（可选）：用项目同一套 LLM，只根据参考答案和原文证据打 0 / 0.5 / 1。它会消耗额度，分数也受该模型本身影响，只能作辅助，不要当成最终标准。

另外会记录一个诊断字段：金标证据在检索片段里是否出现（去掉空白后做子串匹配）。它不是主指标，只用来检查切分或原文是否对得上。

## 建议怎么看结果

先看可回答题的 Hit@1 和 MRR，再看口语题、多跳题有没有明显掉点。如果检索已经很低，先不要把「回答不好」都算到生成头上。不可回答题重点看拒答准确率，以及模型有没有补上材料里不存在的天数、刑期。

改完检索或提示词之后，用同一份 `eval_set.jsonl` 再跑一遍，对比 `summary.md` 即可。题目本身如需增删，直接改 jsonl，保持 `source.articles` 与正文条号一致。
